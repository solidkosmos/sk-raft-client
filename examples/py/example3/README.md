# TEST 3: Targeted injection into essential bits

TEST 1 and TEST 2 flip bits chosen at random from the whole of CRAM, which means
most upsets land on unused logic or routing and do nothing. This example narrows
the target. It loads the design's essential bits data (EBD) alongside the
bitstream, builds the list of bits the design actually uses, and drives
`dev.inject_at()` with those coordinates. Every upset is therefore guaranteed to
hit a bit belonging to the design.

Two modes are offered, chosen interactively when the script starts:

* **Random** picks essential bit locations at random, with replacement, and
  injects `NUMBER_OF_INJECTIONS` of them.
* **Exhaustive** walks every essential bit in the design exactly once.

## What the test does

1. Connects to a running sk-raft server over TCP.
2. Asks for the injection mode.
3. Attaches to the target device (`xc7a35t` by default).
4. Loads the bitstream and the EBD file, then programs the device.
5. Reads back the essential frames and expands them into individual bit
   locations.
6. Injects at those locations, either sampled at random or swept in full.
7. Prints progress every 100 injections.

Injections are **cumulative** in both modes. Nothing is corrected between
iterations, so upsets accumulate for the duration of the run. In exhaustive mode
this means that by the end every essential bit of the design has been flipped.
Reprogram the device before running anything else.

## Requirements

* Python 3.9 or later. The script uses `from __future__ import annotations`, so
  the built-in generic type hints work on older versions too.
* The `skraft` Python package installed in your environment.
* A running sk-raft server with the target board connected to the host over USB.
* A bitstream and a matching EBD file on the **server** filesystem.

## Producing the EBD file

The EBD file is generated by the vendor tools at bitstream time and describes
which configuration bits the design occupies. In Vivado, set the property before
writing the bitstream:

```tcl
set_property BITSTREAM.SEU.ESSENTIALBITS YES [current_design]
write_bitstream -force tester.bit
```

This writes `tester.ebd` next to `tester.bit`. The two must come from the same
implementation run. An EBD from an earlier build will describe bits that no
longer correspond to what is loaded in the device, and the results will be
quietly wrong rather than obviously broken.

One point worth being clear about: essential bits are the bits the design uses,
which is not the same as the bits whose corruption causes a functional failure.
The second set, often called critical bits, is a subset of the first and cannot
be determined from the EBD alone. Injecting into essential bits raises your hit
rate considerably compared with random CRAM injection, but a good share of them
will still produce no visible effect. Finding the critical subset is what the
run is for.

## Configuration

| Constant | Default | Meaning |
| --- | --- | --- |
| `NUMBER_OF_INJECTIONS` | `1000` | Number of upsets in random mode. Ignored in exhaustive mode. |
| `SK_RAFT_SERVER_IP` | `"127.0.0.1"` | Address of the sk-raft server. |
| `SK_RAFT_SERVER_PORT` | `50051` | Port the sk-raft server is listening on. |
| `DEVICE` | `"xc7a35t"` | Target device identifier. Must match a device the server can see. |
| `BITSTREAM` | example path | Location of the `.bit` file, on the server. |
| `EBD` | example path | Location of the matching `.ebd` file, on the server. |
| `WORD_BITS` | `32` | Bits per configuration word. Leave this alone. |
| `PROGRESS_EVERY` | `100` | How often a progress line is printed. |

### About `ServerPath`

Both file paths are wrapped in `ServerPath`, and that wrapper is not decoration.
It marks the path as one to be resolved on the sk-raft server's filesystem, not
on the machine running the script. The client never opens either file and never
uploads them.

When client and server are the same machine this makes no difference. When the
server runs elsewhere, on a lab machine or a shared injection rig, both files
have to exist at those paths **on the server**, and the server process needs
permission to read them. Pointing `ServerPath` at files that only exist on your
laptop is the most common way this example fails. Use absolute paths.

## Running the test

Start the sk-raft server first, then:

```bash
python main.py
```

The script prompts for the mode before it connects to anything, and will keep
asking until it gets a valid answer. It reads from standard input, so for an
unattended run pipe the answer in:

```bash
echo r | python main.py
```

## Choosing a mode

**Random** is the one to reach for most of the time. It gives you a statistical
sample of the design's sensitivity in a bounded amount of time, and the sample
size is yours to set. Watch the design while the run progresses and note the
injection number at which behaviour departs from normal.

**Exhaustive** guarantees complete coverage of the essential bit set, but two
things follow from that which are easy to underestimate:

* The set is large. Even a modest design on a small part can have hundreds of
  thousands of essential bits, and a full part can run into millions. Each
  injection is a read-modify-write over JTAG, so measure your rate on a random
  run first and multiply before committing to a sweep.
* Because the sweep is cumulative and nothing is repaired, the design will
  almost certainly stop working early on, long before the sweep completes. The
  remaining injections then land on a design that is already broken. Exhaustive
  mode is therefore a coverage and stress exercise, not a way to determine which
  individual bits are critical.

To attribute failures to individual bits you need an inject, check, repair loop
that restores each bit before moving to the next. That is a different test, and
neither mode here does it.

## After the run

The device is left with all injected upsets still in place. Rerunning the script
restores a clean configuration as its first action, so no manual cleanup is
needed between runs. Reprogram before any other test that expects a known-good
configuration.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `TEST 3 failed:` with a connection error | The server is not running, or the IP and port do not match. |
| `TEST 3 failed:` on attach | The device identifier does not match anything in the chain, or another process holds the USB connection. Close any open Vivado hardware manager session. |
| `TEST 3 failed:` on load, file not found | One of the paths does not exist on the server, or points at a file that only exists on the client machine. See the `ServerPath` note above. |
| `TEST 3 failed:` on program | Usually a part mismatch. The bitstream must be built for the same device as `DEVICE`. |
| `No essential bits found` | The EBD was not generated with `BITSTREAM.SEU.ESSENTIALBITS` set, or it does not correspond to the loaded bitstream. Rebuild both together. |
| Far fewer essential bits than expected | Check that the EBD belongs to the full design rather than an early or partially implemented build. |
| The design never misbehaves during a random run | Plausible on a small or lightly loaded design, since only a subset of essential bits are critical. Increase `NUMBER_OF_INJECTIONS`, and confirm your monitoring would actually catch a failure. |
| Injections start, then fail partway through | Usually the USB cable or board power dropping out. Reseat the cable and restart the server. |

For anything not covered here, contact SolidKosmos support with the full console
output and the sk-raft server log.
