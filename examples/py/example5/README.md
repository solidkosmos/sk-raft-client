# Fault injection confined to a pblock

The earlier examples treat the device as a single target: upsets land anywhere in
CRAM, or anywhere in the design's essential bits. This one adds a spatial
constraint. It reads the pblock definitions from the design's XDC, works out
exactly which configuration bits belong to the chosen region, and injects only
into those. Every upset stays inside one floorplanned block, and the rest of the
device carries on untouched.

The example design is a Basys3 board with two independent heartbeat generators,
each constrained to its own pblock:

```
pblock_fast_heartbeat   SLICE_X54Y91:SLICE_X57Y99
pblock_slow_heartbeat   SLICE_X62Y56:SLICE_X65Y65
```

Injecting into the fast one and watching both LEDs makes the point directly: the
fast heartbeat stops, and the slow one keeps going. That is
confinement you can see from across the bench.

## Why confine injection

Region-scoped injection answers questions whole-device injection cannot:

* **Partition isolation.** If a design separates a safety-critical function from
  the rest of the logic, this shows whether faults in one region can reach the
  other, which is the sort of evidence a certification argument wants.
* **Redundancy validation.** With a TMR or dual-lane design, confining injection
  to one lane checks that the voter or comparator does its job. Whole-device
  injection cannot guarantee it only ever hit one lane.
* **Sensitivity by region.** Running the same campaign against several pblocks
  in turn shows where a design's fragility actually sits, which is a useful
  input when deciding what to harden.
* **Reproducing field failures.** If you suspect a particular block, you can
  concentrate a campaign there rather than waiting for random injection to find
  it.

## What the test does

1. Connects to a running sk-raft server over TCP.
2. Attaches to the target device (`xc7a35t` by default).
3. Loads the bitstream, EBD and XDC, then programs the device.
4. Lists the pblocks declared in the XDC and picks the named one.
5. Resolves each of its clauses into frames, and each frame into the words and
   bits the pblock occupies.
6. Optionally intersects that footprint with the design's essential bits.
7. Injects `INJECTIONS` upsets at random positions from the resulting set,
   pausing between them so the board can be watched.
8. Reprograms the device to clear the accumulated faults.

Injections are **cumulative** within a run. Nothing is corrected between
iterations, which is the point here: the region degrades progressively while you
watch. The reprogramming at the end restores a clean configuration.

## Requirements

* Python 3.9 or later.
* The `skraft` Python package installed in your environment.
* `reporting.py`, which ships with these examples, importable from the same
  directory.
* A running sk-raft server with the target board connected to the host over USB.
* A bitstream, a matching EBD file and the XDC used to implement the design, all
  on the **server** filesystem.

## Preparing the design

The XDC must declare the pblocks and their ranges, and it has to be the same one
used for the implementation run that produced the bitstream. A pblock that was
added or moved afterwards will resolve to frames that do not correspond to where
the logic actually sits.

```tcl
create_pblock pblock_fast_heartbeat
add_cells_to_pblock [get_pblocks pblock_fast_heartbeat] [get_cells fast_hb_inst]
resize_pblock [get_pblocks pblock_fast_heartbeat] -add {SLICE_X54Y91:SLICE_X57Y99}
```

The EBD is generated by setting `BITSTREAM.SEU.ESSENTIALBITS YES` before
`write_bitstream`, exactly as in the essential-bit examples. It is only needed
when `ESSENTIAL_ONLY` is `True`.

### A word on routing

A pblock constrains where cells are placed. By default it does not constrain
where their nets are routed, so signals belonging to the block can travel
through interconnect well outside the footprint. Two consequences follow.

The injection really is confined: the script computes bits, not approximate
regions, so nothing outside the footprint is ever written. But the *design logic*
associated with the pblock is not fully covered, because the routing that serves
it lies partly elsewhere. A campaign that leaves the block working has shown
that its placed logic tolerated the faults, not that the block as a whole is
immune.

If you want the two to line up, contain the routing as well:

```tcl
set_property CONTAIN_ROUTING true [get_pblocks pblock_fast_heartbeat]
```

This costs timing and area flexibility, so it is a decision to make deliberately
rather than a default to reach for.

## Configuration

| Constant | Default | Meaning |
| --- | --- | --- |
| `SK_RAFT_SERVER_IP` | `"127.0.0.1"` | Address of the sk-raft server. |
| `SK_RAFT_SERVER_PORT` | `50051` | Port the sk-raft server is listening on. |
| `DEVICE` | `"xc7a35t"` | Target device identifier. |
| `BITSTREAM` | example path | Location of the `.bit` file, on the server. |
| `EBD` | example path | Location of the matching `.ebd` file, on the server. |
| `XDC` | example path | Location of the constraints file declaring the pblocks. |
| `PBLOCK` | `"pblock_fast_heartbeat"` | Which pblock to attack, named exactly as in the XDC. |
| `INJECTIONS` | `300` | How many upsets to inject inside it. |
| `PAUSE_S` | `0.1` | Seconds to wait after each upset. Set to `0` for full speed. |
| `ESSENTIAL_ONLY` | `True` | Restrict targets to the pblock's essential bits. `False` uses the whole footprint. |
| `LOG_PATH` | `"pblock_injection.log"` | Transcript file. `None` disables it. |
| `VERBOSE` | `False` | Print per-clause and per-bit detail. |

All three file paths are wrapped in `ServerPath`, which means they are resolved
on the sk-raft server's filesystem, not on the machine running the script. When
the server runs elsewhere, the files must exist at those paths on the server and
the server process must be able to read them. Use absolute paths.

### `ESSENTIAL_ONLY`

A pblock's footprint covers every configuration bit in the region, and most of
those bits belong to logic and routing the design never uses. Injecting into all
of them wastes most of the run on bits that cannot possibly matter.

With `ESSENTIAL_ONLY` set to `True`, the footprint is intersected with the
essential bits from the EBD, so every upset lands on a bit the design depends
on. Expect the target count to drop sharply between the two figures the script
reports, often by an order of magnitude or more, and expect a much higher rate of
visible effects per injection.

Set it to `False` when you want to emulate a realistic radiation environment,
where particles strike unused resources just as readily as used ones, and the
ratio of harmless to harmful strikes is part of what you are measuring.

### `PAUSE_S`

The default of 0.1 seconds is there so a human can watch the LED while the
campaign runs. For an unattended run, or when the effect is captured by
instrumentation rather than by eye, set it to `0`. At the default, 300
injections spend 30 seconds waiting on top of the injection time itself.

## Running the test

Start the sk-raft server first, then:

```bash
python main.py
```

Interrupting with Ctrl-C is safe. The run reports how far it got and closes the
log, but the reprogramming step is skipped, so reprogram the device yourself
before doing anything else with it.

## Expected output

```

Connected, server version 1.4.2
Programmed xc7a35t
Pblocks in the XDC: pblock_fast_heartbeat, pblock_slow_heartbeat
pblock_fast_heartbeat: 41216 CRAM bits in the footprint
pblock_fast_heartbeat: 1834 of them are essential
Injecting 300 upsets into pblock_fast_heartbeat
   #  FAR         WORD  BIT  ELAPSED
   1  0x00020e80    47   19  0:00:03
   2  0x00020e84    12    7  0:00:04
...

Done in 0:01:12
```

Setting `VERBOSE` to `True` adds a line per clause showing how many frames it
resolved to, which is the quickest way to check that a pblock is being
interpreted the way you expect.

Everything printed also goes to the file named by `LOG_PATH`.

## Interpreting the results

The script does not check the design, so the verdict comes from watching the
board. With the example design that means the two LEDs: the targeted heartbeat
should degrade while the other holds its rhythm. Note the injection number at
which the behaviour changes and cross-reference it against the log to recover
the responsible bit.

Points to keep in mind:

* Injections are cumulative, so once the block has failed you cannot attribute
  later behaviour to any single bit. To characterise individual bits inside a
  pblock, combine this targeting with the inject, test, restore loop from the
  BSCAN example.
* Sites are chosen with replacement, so the same bit can be hit more than once,
  and a second hit restores it. With 300 injections drawn from a set of a couple
  of thousand this happens occasionally.

## After the run

The script reprograms the device as its last action, so the configuration is
clean when it exits normally. Reprogram manually if the run was interrupted.

## Troubleshooting

| Symptom | Likely cause |
| --- | --- |
| `ModuleNotFoundError: reporting` | `reporting.py` is not in the same directory or on the Python path. |
| `Failed:` with a connection error | The server is not running, or the IP and port do not match. |
| `Failed:` on attach | The device identifier does not match anything in the chain, or another process holds the USB connection. Close any open Vivado hardware manager session. |
| `Failed:` on load, file not found | One of the three paths does not exist on the server. Use absolute server paths. |
| `... is not declared in ...` | The `PBLOCK` name does not match the XDC. The names actually found are printed on the line above, so compare against those. |
| The pblock list is empty | The XDC contains no pblock definitions, or a different XDC was loaded than the one used for implementation. |
| `Nothing to inject` | The footprint resolved to no bits, or none of them were essential. Confirm the XDC and EBD both came from the same implementation run as the bitstream. |
| Far fewer essential bits than expected | The pblock may be larger than the logic placed in it. Check the utilisation of the block in Vivado. |
| Nothing visible on the LED | The block may have few critical bits, or the logic driving the LED may sit outside the pblock. Try `ESSENTIAL_ONLY` with more injections, and confirm which cells were actually assigned to the block. |
| Both heartbeats stop | Look for shared clocking, reset or enable logic outside both pblocks. |

For anything not covered here, contact SolidKosmos support with the log file and
the sk-raft server log.
